From university weather app to Weather Station

Icons, animation, forecast APIs and interactive maps: how an old coursework dashboard became the current Bootleg OS weather app.

By Oliver Lewis · Updated 20 October 2026 · About 3 min read

In this article

    One project, two stages

    The original university weather application was an Advanced Front-end project: search for a place, ask an API for its weather and turn the response into something readable. Rebuilding it for Bootleg OS gave me a chance to take the same idea further and make the interface feel more like my own.

    The university starting point

    The brief used OpenWeatherMap to display information such as temperature, humidity and wind. That introduced a different kind of interface work: the page was no longer describing a fixed set of facts. It had to respond to whatever location the user searched for and whatever the service returned.

    Loading, unknown places and failed requests were part of the design problem. A dashboard that only looks convincing when the example data happens to work is not finished. The earlier screen is useful evidence of where the project started, but it no longer needs to serve as the thumbnail for the whole story.

    Designing icons instead of just adding numbers

    I made a set of weather graphics for sunshine, cloud, rain, snow and wind. They gave each condition a recognisable shape and helped tie the dashboard together. A useful symbol should work at the small size where it will actually be read, not only as a large image in a design file.

    The graphics also open up animation ideas: a slow-moving cloud, rain passing through a loop, or a sun that feels warmer without making the whole page distracting. The old project explored SVG and clock animation. In the current work, I want motion to communicate a state while keeping the text available and respecting reduced-motion preferences.

    From a name to a forecast

    The current Weather Station uses Open-Meteo’s geocoding search to resolve place names, then requests forecast data for the chosen coordinates. The screen combines current conditions with hourly and daily outlooks instead of making the user interpret a raw response.

    Geolocation offers another way to choose a place, with the browser asking for permission first. The page still needs a typed search for people who prefer not to share their location or whose device cannot provide it.

    Place search→Coordinates→Forecast response→Readable cards

    Putting the forecast on a map

    Leaflet supplies the interactive map, OpenStreetMap provides its base tiles, and the configured weather overlay uses OpenWeatherMap tiles. Moving the forecast to another place should update the marker and the surrounding view together.

    Those are separate services. A readable forecast can still be available when an overlay is missing or an API limit has been reached. Labelling the layer and showing a useful fallback is better than presenting every tile as an infallible live measurement.

    Try the current version

    Open Weather Station →
    Search a place, compare the forecast cards and explore the map layers. Live data depends on the providers being available; an hourly forecast is not the same as a real-time sensor reading.

    What comes next

    The useful work now is in the details: clearer map legends, more consistent weather symbols, less crowded phone layouts and animations that help rather than compete with the forecast. News, clocks and weather can share an interface without all demanding attention at once.

    I like revisiting this project because the first version still has value. It taught me how to ask for data. The current one is teaching me how to give that data a better home.
